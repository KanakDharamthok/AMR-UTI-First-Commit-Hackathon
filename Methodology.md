## 3. Methodology

### 3.1 Problem Formulation

This work develops a machine-learning-based clinical decision-support system for estimating antimicrobial susceptibility in urinary tract infection (UTI) cases. The system operates on structured patient- and specimen-level features and produces susceptibility probabilities for four antibiotics:

* Nitrofurantoin (NIT)
* Trimethoprim-sulfamethoxazole (SXT)
* Ciprofloxacin (CIP)
* Levofloxacin (LVX)

The underlying AMR-UTI dataset is derived from electronic health-record data from Massachusetts General Hospital and Brigham and Women's Hospital and contains microbiological susceptibility information together with patient, specimen, and treatment-related variables. The original resource was designed specifically to support algorithms for empiric UTI treatment and antimicrobial-resistance prediction.

The released dataset defines resistance labels from microbiological susceptibility testing and treats intermediate and resistant phenotypes as resistant. Its original train/test construction is chronological, with training observations from 2007–2013 and test observations from 2014–2016, while avoiding patient overlap between the uncomplicated-UTI training and test cohorts.

In this project, the learning problem was subsequently converted into a locked inference contract. The deployed model receives exactly 788 ordered input features and produces four susceptibility probabilities:

$$
f_\theta:\mathbb{R}^{788}\rightarrow[0,1]^4
$$

where the four output dimensions correspond to NIT, SXT, CIP, and LVX.

The objective of the deployed system is not to replace microbiological testing or independent clinical judgment. Rather, it exposes the trained model as a reproducible decision-support component whose predictions remain subject to clinician review.

---

### 3.2 Feature Contract and Data Provenance

A central design principle was to prevent the deployment layer from reconstructing or inferring the training feature schema.

A locked `feature_names.json` artifact was therefore created as part of the modeling contract. The artifact contains exactly 788 feature names and defines the ordering expected by the certified model.

The final feature contract was independently checked during deployment:

* feature contract exists;
* feature count = 788;
* feature ordering is explicitly represented;
* Script 37 reads the locked feature contract;
* the application refuses to invent a missing feature schema.

This distinction is important because a model accepting a vector of the correct dimensionality is not necessarily receiving the correct variables in the correct order. The deployment implementation therefore treats the feature schema as a versioned artifact rather than an implicit assumption.

Representative features include demographic variables, historical resistance indicators, microbiological variables, and temporally constructed features. The project retained the feature representation used by the trained model rather than introducing a new preprocessing or feature-selection stage during deployment.

---

### 3.3 Certified Model Artifact

The final trained model was not retrained during application deployment.

Instead, the application loads the previously trained and certified model artifact generated by the preceding modeling pipeline. The deployed artifact is identified by a SHA-256 fingerprint:

`db708f2c18a9390d72af1c520dab460374a737ced00e8c7ec76e3ac315bcc318`

The application verifies this fingerprint before accepting the model as valid.

The model contains **52,978 parameters** and is identified internally as the certified `FullHybridModel`. The deployment process also verifies the SHA-256 fingerprint of the quantum-contribution/ablation implementation used in the certification chain:

`12d2d201c9153253632383c598b8e360bcc5dc61b0492bf4233b406d7b6cdb3a`

Thus, the deployed inference service does not silently substitute a newly trained model, modify model parameters, or alter the underlying quantum contribution.

### 3.5 Quantum-Hybrid Model Architecture

The deployed model is the final `FullHybridModel` produced by the project's preceding quantum-modeling pipeline.

The deployment layer deliberately does not replace the trained architecture with a generic API model, language model, or externally hosted AI service. Prediction requests are evaluated by the locally loaded certified model artifact.

The distinction is important for reproducibility: the HTTP API is only the transport/interface layer. The predictive computation occurs inside the project's own certified inference engine.

The system therefore follows the following chain:

$$
\text{788-dimensional feature vector}
\rightarrow
\text{certified FullHybridModel}
\rightarrow
\text{four susceptibility probabilities}
\rightarrow
\text{locked threshold}
\rightarrow
\text{clinical decision-support response}
$$

---

### 3.6 Locked Decision Threshold

A threshold of 0.5 was retained as the locked classification threshold.

For an antibiotic \(a\), let \(p_a\) denote the model-estimated susceptibility probability. The classification rule is:

$$
\hat{y}_a =
\begin{cases}
1, & p_a \geq 0.5\\
0, & p_a < 0.5
\end{cases}
$$

The deployment implementation explicitly reports the threshold and records that threshold optimization is disabled.

The deployed model therefore does not modify its decision threshold based on the incoming patient, request distribution, or deployment environment.

Similarly, calibration is not fitted during inference. The API explicitly reports:

```text
threshold_optimization: false
calibration: false
model_training: false
official_test_usage: false
```

This prevents the deployment stage from inadvertently becoming a second training or optimization stage.

### 3.7 Inference Pipeline

For each prediction request, the system performs the following sequence:

**Step 1 — Request validation**

The API accepts a JSON object containing a list named `features`.

**Step 2 — Feature validation**

The feature vector is validated against the locked 788-dimensional contract.

**Step 3 — Authentication**

Protected endpoints require the `X-Clinician-Api-Key` HTTP header.

**Step 4 — Model inference**

The validated vector is passed to the already-loaded certified inference engine.

**Step 5 — Probability generation**

The model produces four susceptibility probabilities.

**Step 6 — Locked classification**

Each probability is compared with the fixed 0.5 threshold.

**Step 7 — Diagnostic metadata**

The system calculates minimum, maximum, mean probability, and distance from the locked threshold.

**Step 8 — Provenance reporting**

The response contains the model fingerprint, Script 30 fingerprint, parameter count, feature count, model version, and engine version.

**Step 9 — Clinical-use boundary**

The response explicitly identifies the output as clinician decision support and not as a diagnosis, prescription, antibiotic recommendation, or dose recommendation.

---

### 3.8 Clinician-Facing API

The inference engine is exposed through a FastAPI application.

The API contains three application-level endpoints:

| Endpoint      | Method | Function                                  |
| ------------- | -----: | ----------------------------------------- |
| `/health`     |    GET | Service and model health/provenance check |
| `/model-info` |    GET | Authenticated model metadata              |
| `/predict`    |   POST | Authenticated model inference             |

FastAPI also automatically exposes the OpenAPI schema at `/openapi.json` and documentation interfaces at `/docs` and `/redoc`.

The `/health` endpoint intentionally remains lightweight and reports the application version, model version, model fingerprint, feature count, and target antibiotics.

The `/model-info` and `/predict` endpoints are protected by the clinician API key.

---

### 3.9 Authentication and Access Control

The project implements an application-level API-key boundary rather than exposing protected prediction endpoints without authentication.

A clinician API key is supplied through the `X-Clinician-Api-Key` header.

Unauthenticated access to `/model-info` is rejected with:

```text
401 Unauthorized
CLINICIAN_API_KEY is not configured.
```

After configuration of the local development key, authenticated requests successfully accessed `/model-info` and `/predict`.

The authentication mechanism is intended as an application access-control mechanism. It should not be interpreted as a complete clinical security architecture; production deployment would additionally require secure secret management, transport security, identity management, auditing, and institutional controls.

---

### 3.10 Local Containerization

The final application was containerized using Docker.

The container build includes:

* Python 3.11 runtime;
* deployment requirements;
* the complete Script 37 inference application;
* the locked `modeling_contract`;
* certified model artifacts contained in `audit_outputs`;
* the Cloud Run entrypoint.

A critical deployment issue was identified during the first containerization attempt: the model application uses an absolute project-root convention,

```text
/root/uti_amr_quantum_pipeline
```

while the initial Docker image placed the project at `/app`.

As a result, the model artifact existed inside the container but Script 37 could not locate it at the path expected by the certified code.

The container was subsequently rebuilt with:

```text
WORKDIR /root/uti_amr_quantum_pipeline
```

and the required project directories were copied into that exact location.

This correction allowed the certified feature contract and model artifact to be discovered without modifying Script 37 itself.

## 4. End-to-End System Architecture

The resulting architecture can be represented as five layers.

### Layer 1 — Clinical Data

Patient/specimen-derived features from the AMR-UTI modeling pipeline are represented using the locked 788-feature schema.

### Layer 2 — Certified Model Artifact

The 788-dimensional feature vector is processed by the previously trained `FullHybridModel`.

### Layer 3 — Production Inference Engine

The certified model is loaded by the Script 37 clinician decision-support application. Integrity checks are executed before predictions are served.

### Layer 4 — API Interface

FastAPI exposes:

* health verification;
* model metadata;
* prediction inference.

Protected operations require clinician API-key authentication.

### Layer 5 — Decision-Support Response

The service returns:

* susceptibility probability for each antibiotic;
* threshold-based classification;
* probability-band metadata;
* inference diagnostics;
* model provenance;
* clinical-use boundary information.

The system therefore separates **model development**, **model certification**, **model loading**, and **model serving** rather than retraining or modifying the model during deployment.

## 11. Reproducibility and Auditability

The implementation emphasizes reproducibility at three levels.

### 11.1 Computational reproducibility

The exact model artifact is identified using SHA-256 rather than relying only on a filename or mutable `latest` tag.

### 11.2 Schema reproducibility

The exact 788-feature ordering is stored separately in the modeling contract and validated during application startup.

### 11.3 Runtime reproducibility

Every prediction response contains the application version, model version, engine version, model fingerprint, Script 30 fingerprint, parameter count, and feature count.

The prediction service therefore exposes sufficient provenance information to associate an inference result with a specific model artifact and inference implementation.

## 12. Deployment Lessons and Engineering Actions

Several engineering failures encountered during deployment were treated as reproducibility tests rather than silently bypassed.

### 12.1 Incorrect project-root location

The first container used `/app` as its working directory. Script 37 expected:

```text
/root/uti_amr_quantum_pipeline/modeling_contract/feature_names.json
```

The application consequently failed certification despite the feature file being physically present elsewhere in the container.

The resolution was to reproduce the expected project-root structure inside the container rather than modifying the certified model code.

### 12.2 Missing deployment artifact

An early deployment image did not contain `modeling_contract/feature_names.json`. Script 37 correctly rejected the deployment rather than constructing a feature schema automatically.

This behavior is desirable for a reproducible model-serving system because silently inventing or reconstructing a feature order could produce valid-looking but scientifically invalid predictions.

### 12.3 API root versus application endpoints

A request to `/` returned HTTP 404. This was not a model failure.

The application intentionally exposes its functional routes at:

```text
/health
/model-info
/predict
```

and its OpenAPI schema at:

```text
/openapi.json
```

Consequently, testing the root URL alone is insufficient to determine whether the model service is operational.

### 12.4 Authentication boundary

The `/model-info` endpoint initially returned HTTP 401 because `CLINICIAN_API_KEY` was not configured.

After providing the development API key and corresponding request header, the endpoint returned HTTP 200.

This demonstrated that the authentication mechanism was active rather than merely declared in the source code.

### 12.5 Successful end-to-end correction

After correcting the container root, feature-contract inclusion, and API-key configuration, the complete local inference path succeeded:

```text
Docker image
      ↓
Container startup
      ↓
Certified model loading
      ↓
Integrity verification
      ↓
FastAPI startup
      ↓
/health → 200
      ↓
/openapi.json → 200
      ↓
/model-info → 200
      ↓
/predict → 200
      ↓
Four model probabilities returned
```

## 13. Scope of the Evidence

The experiments establish that the certified model artifact can be loaded reproducibly and executed through a locally containerized clinician-facing API.

The evidence establishes:

* model artifact integrity;
* feature-contract integrity;
* successful model loading;
* successful forward inference;
* API availability;
* authentication behavior;
* successful end-to-end prediction;
* provenance reporting.

However, these deployment experiments do **not** by themselves establish:

* clinical effectiveness;
* prospective clinical utility;
* generalization to another hospital;
* calibration in a new population;
* superiority over standard clinical practice;
* causal benefit from the model;
* improved patient outcomes.

Those claims require separate evaluation using appropriately designed validation, external-cohort, prospective, or clinical-impact studies.

This distinction is particularly important because the underlying AMR-UTI resource was designed for antimicrobial-resistance and empiric-treatment research, but a successfully deployed model should not be presented as clinically validated merely because its software and artifact integrity checks pass.

## 14. Project Contribution

The principal contribution of the project is therefore not only the trained quantum-hybrid model. It is the construction of a **traceable model-to-inference pipeline** in which the trained artifact, feature representation, certification evidence, inference engine, authentication layer, and runtime interface are explicitly connected.

The resulting system transforms the research model into a reproducible computational artifact:

$$
\boxed{
\text{Data}
\rightarrow
\text{Locked Features}
\rightarrow
\text{Trained Quantum-Hybrid Model}
\rightarrow
\text{Certification}
\rightarrow
\text{Production Inference Engine}
\rightarrow
\text{Authenticated API}
\rightarrow
\text{Auditable Prediction}
}
$$

This separation between model development and model serving allows the final inference environment to consume the already-certified artifact without retraining, recalibration, threshold optimization, or feature-selection changes during deployment.

The system consequently provides a concrete bridge between experimental quantum machine learning and reproducible clinical decision-support software, while retaining an explicit boundary between computational prediction and clinical decision making.
